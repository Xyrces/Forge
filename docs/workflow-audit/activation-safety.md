# Sprint activation safety increment

This increment repairs admission and publication correctness, not sprint planning policy.

- Automatic assembly, proposal commits, and legacy HTTP activation use `SprintActivationValidator`. Executable selections must be nonempty, distinct, pending, technically groomed (directly or through a Groomed specification), owned by the target project, unsprinted in another active sprint, and unblocked under the existing readiness rule. Containers are display membership, never executable selections.
- Proposal previews retain their scored candidate fingerprints (task, ancestry, specification version/body) in the existing audit. Commits reject arbitrary selections, changed snapshots, legacy audits without fingerprints, and already-committed proposals. Preview validation loads the issue/eligibility context once and caches specification reads.
- `SprintStore.CreateWithIssuesAsync` uses a serializable transaction for active-sprint conflict checking, exact issue/specification revalidation, open prerequisite checking, sprint creation, membership, and the proposal committed marker. The activation event is published only after all membership commits. Rollback leaves no partial active sprint. Concurrent attempts cannot both create active sprints; SQL Server may reject one with a deadlock rather than a friendly conflict.
- Creating/activating another sprint never implicitly archives the existing active sprint. Existing-sprint HTTP activation also rechecks its exact membership in the transaction. The legacy HTTP create contract has no task selection, so an Active creation fails validation; archived creation and non-activation edits remain available.
- Manual additions to an active sprint use the same eligibility/ownership/grooming checks and transactional row revalidation. Additions to inactive sprints are fenced against a concurrent activation, preserving draft membership editing without creating a race around active validation.

Stage gates retain **check-at-evaluation** semantics. Gate state is checked before activation, not atomically with target-project membership: global gates can live in a different database. A hold arriving during an already-running activation is not a distributed transaction fence. This increment adds no cross-store coordination architecture.

Existing automatic membership exceptions remain deliberate: `FollowUpTool` immediately attaches a genuine blocker of active work before grooming (the existing urgent-blocker policy; dispatch still applies grooming), and intake can attach an epic as display membership. The assembler's existing amendment/grouping policies remain unchanged. This is not a claim that every display or urgent membership row is an executable, groomed task.

No new task cap, outcome/provenance model, initiative approval policy, dependency-closure selection, failure aging, or closed/completed semantics are introduced. Six of the seven original planning characterizations remain unresolved policy/design work; the proposal-displaces-active characterization is now a rejection regression.

Validation covers stale task/specification snapshots, a prerequisite arriving after validation, arbitrary/ungroomed/container/cross-project proposals, held gates, atomic rollback after partial membership insertion, competing activation, immutable proposal commit markers, project-routed HTTP activation and manual membership, numeric status values, and bounded preview database reads. SQL Server code paths use the existing provider seam; no live schema changes or paid model requests are involved.
