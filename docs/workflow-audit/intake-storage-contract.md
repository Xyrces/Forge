# Initiative storage contract (M040)

This increment implements Core persistence only. Agents, HTTP approval routes, Proposals navigation, and controller recovery scheduling integrate separately. No migration or production operation was executed by this change.

`InitiativeProposalStore` uses the existing primary Intake store. Source identity is unique per project/source key; replay returns the existing identity and refuses conflicting origin, provenance or explicit session rebinding. Payload revisions are immutable and their SHA256 hashes bind project/title/body/priority. Approval requires the current exact revision/hash, a linked project-owned Intake session, and explicit operator attribution. Attribution is a recorded caller description, not a claim that the currently unauthenticated dashboard proves a human identity. A model tool must not receive this approval capability.

`ExpandInIntakeAsync` creates the conversation and its source context atomically with the proposal link. Repeated expansion returns that same conversation. `ListAsync` and `ListApprovedAsync` return bounded summaries without body/provenance payloads, ordered by stable proposal ID; continue using the final ID as `afterId`. Session filtering occurs before SQL row limiting. `GetAsync` retrieves full selected content. Approved-list queries include only proposals awaiting ingestion acknowledgement. Recovery must continue through batches rather than treating one batch as the whole queue.

`InitiativeIngestionStore` belongs to the target project's IssueStore. The coordinator supplies an approved snapshot reloaded from ProposalStore; the record parameter is an internal integration contract, not an externally trusted HTTP request. The store rejects a different project or damaged payload hash. A unique proposal/revision receipt, epic, Draft spec, spec version/extraction, and issue creation event commit in one target transaction. Existing IssueStore and SpecStore creation methods share internal transaction bodies; TaskEnqueued publishes only after commit. The normal JSONL mirror still reads IssueStore as source of truth. No separate engineering queue or active-sprint injection is introduced.

After a target commit but before primary acknowledgement, replay returns the same target receipt. The coordinator then calls MarkIngestedAsync idempotently; conflicting epic/spec links fail. A durable Pending refinement receipt survives lost events. Claim is a conditional Pending-to-Running transition. Completion atomically advances Draft to ReadyForDesign (or recognizes already ReadyForDesign) and marks Completed, then publishes the normal spec event. Other spec states fail closed rather than resetting design/grooming work.

Failed model work remains Failed. At exclusive-controller startup, RecoverRunningAsync also marks interrupted Running work Failed/uncertain; it does not spend again automatically. Explicit RetryRefinementAsync is required to return Failed to Pending. Callers must join old local work before startup recovery/retry; this local receipt does not replace the controller ownership fence or authorize concurrent controllers. Refinement status writes serialize with ingestion/completion through a short per-schema database lock row; no HTTP/model work occurs while that lock is held.

M040 adds four tables only: initiative_lock, initiative_proposal, initiative_revision, initiative_ingestion. SQLite and SQL fresh/upgrade paths use the same guarded shape. Existing tables/data are unchanged, and the new runtime requires exact schema40. Compatibility with a rollback image must be independently qualified; this commit does not broaden accepted schema versions or implement unattended migration.

Offline coverage includes concurrent suggestion/expansion/ingestion, stale approval and hash rejection, immutable revision history, honest first-operator preservation, project/session isolation, source-binding conflicts, bounded session-filtered summaries, injected failure during spec creation rolling back epic/event/receipt, replay after missing primary acknowledgement, unique refinement claims, explicit retry, interrupted work, atomic completion and migration idempotence. Actual SQL Server rehearsal remains a separate qualification step.
