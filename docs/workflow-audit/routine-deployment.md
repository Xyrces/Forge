# Routine qualified deployment

Routine delivery is opt-in through the Forge project's Kubernetes deployment profile (`routineEnabled: true`). It follows the shared durable sprint-completion receipt; it does not treat arbitrary pushes, task prose, a local checkout, or a PR head SHA as authority. The completion evaluator must mark engineering evidence ready before this coordinator creates a candidate. The planner's next-sprint barrier uses the same completion-to-candidate binding.

The controller observes each recorded PR through GitHub, verifies that it is actually merged into the configured repository and branch, and identifies a merge-commit frontier containing the other observed merges. That frontier is pinned to the completion receipt. A deterministic candidate ID and unique completion binding recover interruption between candidate creation and receipt acknowledgement without creating duplicate releases.

Qualification checks successful push runs of both the configured validation workflow (`ci.yml`) and image workflow (`controller-image.yml`) at that exact source. It verifies workflow identity, repository, branch, source and event, then downloads the image receipt artifact with bounded reads. Artifact SHA-256, archive contents, source/run identity, configured image repository, immutable digest and schema version must all agree. A newer failed or unfinished run cannot fall back to an older green run. Artifact redirect downloads use a separate client without GitHub bearer credentials. GitHub documents the relevant run metadata and artifact digest/download fields in its [workflow runs API](https://docs.github.com/en/rest/actions/workflow-runs) and [artifacts API](https://docs.github.com/en/rest/actions/artifacts).

Verified evidence is pinned immutably in the deployment row. Routine candidates therefore need no operator catalog registration and no controller permission to write the Kubernetes image catalog. The existing catalog remains the explicit manual/bootstrap path. Worker writes to deployment and completion authority tables must be denied by the initializer.

Missing, unfinished or unsuccessful CI remains awaiting qualification and is rechecked. A held `deploy` gate prevents automatic approval and admission of a not-yet-created release Job, including recovery after approval. Existing Jobs continue reconciling. Hold/release is available on the Flow workflow controls; releasing it resumes the same candidate on the 15-second durable reconciliation loop. Dashboard reads never start a missing Job. The running image's source must be an ancestor of the candidate, preventing an automatic rollback to an older sprint source. Routine delivery only supports the current schema version. Bootstrap credentials, first installation and schema changes remain separate qualified operations.

The coordinator starts after controller readiness and is joined at shutdown. Every 15 seconds it reconciles durable unbound completions and directly queries nonterminal deployment rows with keyset pagination. It does not depend on a browser visiting deployment history. The independent release Job still owns cutover, SQL ownership transfer and rollback. Its journal is the completion evidence; stale progress observations cannot overwrite a terminal outcome. Failed/rolled-back candidates are not automatically retried.

Offline tests cover delayed CI, exact merged-source observation, forged repository/branch/source/event/artifact/image/schema evidence, credential-free redirects, duplicate completion delivery, interrupted binding, held gates, terminal rollback, pinned receipts without a catalog, and pending operations older than the history window. These tests make no paid requests and do not qualify a live rollout by themselves.

The Sprints page separates task-board counts, engineering evidence, follow-up processing, and release state. Its outstanding-completion overview is collapsed by default and reads five bounded summaries per page; selected completion batches use independent pagination. Missing or failed responses show unknown/unavailable state, never an inferred successful delivery. Explicit operator-observed criteria remain unproven until source-bound observation evidence is recorded.

Stopping an unresolved typed outcome is an explicit operator action with a required reason and exact plan identity. It preserves the original outcome and evidence; it does not manufacture success. A pending, unstarted routine release can be rejected through the ordinary deployment controls. An authorized or running independent release must reach a safe terminal result before the outcome can be stopped. Backend abandonment and captured delivery-policy behavior are defined by the shared completion store, not by UI visibility alone.

The completion projection has a separate paged recovery scan for bound receipts, so a controller interruption after the deployment row becomes terminal cannot strand its evidence update. The delivery barrier must distinguish engineering criteria already satisfied from an enabled routine release still awaiting completion; those are separate facts.
