# Human review, sprint tasks, and run history

**Proposed plan for discussion · November 17, 2026.** The reference build is Forge main `30a6ec9`. The operator should be able to see what a task is doing, why it returned for work, who acts next, and whether to reserve its PR for human review. The starting point is the active sprint, including tasks already in rework.

## The operator's path

1. Open **Sprints**. The selected sprint's goal and progress sit above its Kanban board. In **Running**, a card titled “Remove the broken script from the dashboard” says “Making a requested change” and names the worker responding to the review. Clicking the title opens that task. The PR number links directly to GitHub.
2. Open **Task actions → Require my review** on the card or in task detail. Once saved, the card shows “Human review required before merge.” If no PR exists yet, Forge remembers the request. While the worker is fixing code, the card stays in **Running**.
3. When the selected human can act, the card moves to **Needs you**, says why, and offers **Review PR #150**. GitHub supplies the diff, inline threads, and formal review. If the person requests changes, Forge routes the actual findings back to the worker. If they approve the current revision and all other required checks pass, Forge can merge.
4. After merge, the card says **Merged** in **Completed / closed**. The sprint separately reports deployment and any outstanding browser acceptance. The operator can still inspect the earlier failed check, review feedback, and recovery. Returning from task or run detail restores the selected project, sprint, lane, filter, and position.

“My review” needs a person behind it. Today's dashboard receipt identifies a shared operator. With a single configured human, the action can say **Request review from Xyrces** and show that GitHub reviewer by name. Where no individual can be established, use **Require human review** and show the project's eligible reviewers. An authenticated click requests a hold. A formal GitHub decision establishes who reviewed the code.

## Status and history rules

| Evidence | Operator-facing interpretation |
| --- | --- |
| Reviewer finishes and requests a change | Run **Review completed**. Task **Changes requested** or **Making a requested change**, depending on whether a worker has started. Link to the finding. |
| CI fails and Forge can recover | **CI failed · Fix queued**, with the failed check, next actor, and a link. Keep the failed check in history after recovery. A provider outage that automatically resumes reads **Waiting for reviewer service**. |
| Human review was requested | While work continues, keep the current work status and a secondary review requirement. Once ready, show **Waiting for human review**. No worker slot, paid retry, strike or stale-task failure accrues during that human wait. |
| One verdict is delivered repeatedly | Count one actionable request. Record one rework round when Forge actually acts on it. New findings can join the open round. Show review decisions, fix attempts and operator retries separately. Never turn a raw strike counter into a historical count of independent failures. |
| Model returns but worker verification continues | Show **Verifying changes**. If the worker loses publication authority, show **Change prepared · Publication stopped** with the recorded reason. The model run, worker outcome and task can legitimately have different results. |
| Work stops | **Needs you** when Forge has exhausted its supported recovery or needs a decision. Distinguish cancellation, supersession, verified existing implementation, and observed merge. A genuine failed attempt retains its error, time and link. |
| Old, incomplete or stale data | Examples include **Completion recorded · Merge evidence unavailable**, **Earlier run · Association unknown**, and **Couldn’t load history · Retry**. Preserve the last confirmed view with its timestamp when refresh fails. |

Build one typed, project-scoped read model for these labels. Reuse the task state machine, current-head review/CI facts, failure ledger, worker receipts, trusted publication and sprint completion records. Extend the existing situation presenter and have list/detail views share components and styles. Keep writes in the existing owners. Return the status, reason, next actor, evidence reference, freshness and allowed actions together. Correlate future runs by durable attempt identity. Keep older ambiguous records at task level. Expose safe summaries and page history with a real continuation. Never send raw worker assignments or credentials to the browser. ## Review contract

PR #148 had a changes-requested round and an approval recorded as two ordinary comments. GitHub recorded zero formal reviews. Forge already attempts a formal review, but its publishing identity authored the PR. The pilot's last merge used the repository owner's ruleset bypass. Both facts matter when testing whether GitHub itself can stop a merge. [PR #148](https://github.com/Xyrces/Forge/pull/148) · [Review publication](https://github.com/Xyrces/Forge/blob/30a6ec9/Reviewer/ReviewerDispatcher.cs) · [Merge audit](https://api.github.com/repos/Xyrces/Forge/rulesets/rule-suites/5192827073)

- **Modes.** The project can use automated approval, human approval, or both. A mid-sprint hold adds the human requirement to the effective policy. QA and CI continue in every mode. Any outstanding formal change request from an authorized human blocks automatic merge. Ordinary human comments are advisory. Releasing a task hold removes only that additional requirement. It cannot waive project policy or dismiss a person's formal objection.
- **Two ways in.** GitHub's `needs-human-review` label and the task action operate the same hold. Before PR creation, Forge owns the pending intent. Once the label is confirmed, reconcile external edits against GitHub. While synchronization is uncertain, keep the merge held and show the sync state. Record who requested or released it when known. Respect a PR already merged or closed, including an external merge during a hold.
- **Distinct identities.** Use separate repository-scoped GitHub Apps for publishing work and for automated review. The controller obtains short-lived installation credentials. The reviewer key stays outside engineering pods, and routine merge uses an identity subject to branch protection. Confirm in a disposable protected repository that an approval actually counts and a late human objection stops a merge. Existing projects can migrate explicitly. Surface identity or permission failures as integration problems. [GitHub App installation authentication](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation)
- **One review per revision and attempt.** Publish a formal Approve, Request changes or Comment with a concise summary. Put each local finding on a validated diff line or range. Explain cross-file, runtime and unanchorable findings in the summary. On a retry after an uncertain publish, look up the existing review before posting. Bring human review text and inline threads into the corresponding rework round. A successful “changes requested” review counts as a completed reviewer run. [GitHub review API](https://docs.github.com/en/rest/pulls/reviews#create-a-review-for-a-pull-request)
- **Timing.** GitHub label, review and check events should wake the owning task via Talaria. Include authenticated event delivery, duplicate handling and a reconciliation path for lost events on the existing private host. Re-read the live label, effective authorized reviews and exact head immediately before merge. Fresh commits require current-head approval. A prior formal human objection remains blocking until cleared by the appropriate human or an authorized explicit dismissal. A refused merge triggers a fresh read and the corresponding waiting state. A SHA condition guards code changes. A last-second label edit can race the merge, as can a human objection on an unprotected repository. Expose the hold before dispatch when the operator wants certainty from the outset. [Forge watcher](https://github.com/Xyrces/Forge/blob/30a6ec9/Reviewer/PRWatcher.cs) · [GitHub merge API](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request)

### Acceptance with an operator

- At 1280 px with the sidebar open, verify that the entire rightmost lane and its cards fit. At 390 px, reach every lane and read its cards and actions without horizontal clipping. At both widths, find a card in rework, explain what triggered it and who acts next, request review, and locate the relevant run or GitHub diff. Proposed targets for discussion are **10 seconds** to identify the reason/next actor and **two interactions** from a visible card to request review. Confirm the card stays in Running while the worker works and moves to Needs you when human review is ready. Measure discovery time with a person. Browser automation can verify interaction count and saved state.
- Check keyboard access, screen-reader names, focus after menus and refresh, wrapped titles and actual card bounds inside the available content area. No hover-only reason or color-only failure. Preserve links and readable historical views across project switches, including duplicate task IDs in different projects.
- Exercise all review modes, pre-PR and mid-rework holds, external label changes, duplicate and out-of-order webhooks, and a new push. Cover a human wait beyond the existing 24-hour window, an already-merged PR, a missing integration, a rejected merge and a controller restart. Validate one human changing their decision on the same revision and multiple reviewers disagreeing. A normal comment never triggers a paid fix on its own.
- Keep the read changes additive for existing callers. Rehearse new persisted review or worker-attempt fields against Azure SQL and the supported test provider. Rollback must preserve recorded human holds. If the prior controller cannot honor those holds, pause automatic merging during rollback and reconcile them before resuming it.
- Run fixtures, UI tests and replay on Linux first. Compare the redesign with today's screenshots and the same task data. Then run one authorized end-to-end pilot under the existing spending ceiling and verify the exact deployed revision in the browser. Save both the failure evidence and the recovered outcome.

**Decision for the design review.** Confirm how a dashboard user chooses the required human when several people can review. For the current single-operator installation, nominate the repository owner and display their GitHub name. The rest of the interaction can be tested with that default.
